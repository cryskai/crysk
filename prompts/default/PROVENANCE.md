- **Modifications (2026-11-15, finding contract):** Body change in all four hunter prompts. Each prompt's own severity section (`## 6. No-Self-Filter Mandate` in logic, resilience and parity; `### Severity — answer the hypothetical, then stop` in reliability) is replaced by one `Finding contract` section, byte-identical in the four (`test/review/bundled-prompts-finding-contract.test.ts`). It says what a finding consists of (fact, trigger, consequence, in that order, and which links were read), defines `severity` by the consequence taken as if the trigger happens, and defines `evidence_class` and `causal_disposition`, which no hunter but reliability defined before although the tier rule reads both. Decided by the owner on 2026-11-15: the consequence sets severity; an irreversible consequence or a security boundary crossed is `BLOCKER` even when the trigger is uncommon, as long as a user or a caller can cause it; `WARNING` is for wrong behaviour that can be recovered from and needs a condition the claim names. Removed with the old sections: a ladder written for a user interface ("stuck spinner, wrong rendered values, dead control"), "latent-until-triggered → `WARNING`", and "emit the finding anyway", which the engine's read requirement contradicts. Reliability keeps its two worked calibrations after the contract. No schema field is added: the three links are a writing rule for `claim`. Revised the same day after the review of the first version: the severity rule is stated in two steps (an irreversible or security consequence is `BLOCKER` whatever the trigger; otherwise ordinary operation gives `CRITICAL` and a named condition gives `WARNING`), because "from the third link alone" contradicted a ladder that separated two levels by the trigger; and three lines outside the section that gave `claim` another shape, put likelihood in `evidence_class`, or sent a defect in unchanged code to `pre-existing` were brought in line with it. A second review pass found two more of the same kind, and the rest of the four prompts was then read line by line for it: the noise rules of parity and resilience ("distinguish diff-introduced from pre-existing risk and down-weight the latter") now name `causal_disposition` and say not to lower severity for it; and the contract says that being unsure a trigger happens is not a named condition, which reliability's first worked calibration now repeats instead of calling that doubt "the trigger link". The same pass showed a hole in step 1: an irreversible consequence whose trigger no user or caller causes (a dependency failing part-way through a write) fell through to `WARNING`; the trigger is now anything that can happen in the running system, a failure the system has to expect included. Left as it is, for the division-of-labour slice: "weigh fix cost against realistic benefit" in parity and resilience.
- **Additions (2026-11-15, security hunter):** New file `deep-review-security.md`, key `security`, written for this set (it has no upstream). It runs on every review, beside reliability, resilience and logic. Its question is whether a change lets someone do or see what they are not entitled to, asked of every changed hunk in four parts: outside input reaching something that interprets it, an operation on something that belongs to someone, a control the change removes or steps around, a secret outside its place. It lists what it does not report (input only a trusted party can supply, values the system produced, a control that holds, hardening with no path, dependencies, tests and placeholders, style). It carries the shared `Finding contract` section, byte-identical to the other hunters, and reports under the existing category 4, so the findings schema does not change. The other five prompts are byte-identical. Measured the day it was written, single runs: 5 of 5 planted defects found and rated blocking, 0 of 4 correct look-alikes reported, and 0 findings on 7 changes with no security defect. Read those numbers with their limit: the six synthetic cases were built by an agent that did not see the prompt, but their defects and look-alikes were specified by the prompt's author, and the prompt names the same shapes, so on them the result is in-sample (the prompt follows its own text; it says nothing about other shapes). The independent sample is six real commits from four projects: one path-escape defect found, five changes with no security defect left alone. On the four synthetic defects the logic hunter also found 4 of 4, so these cases show no defect the set missed before; what the new hunter adds beyond them is not measured. In one full local review of one of those cases all four always-on hunters reported the planted defect, the merge step folded them into one finding and the refuter corroborated it; the new hunter was 13% of that review's notional cost.
